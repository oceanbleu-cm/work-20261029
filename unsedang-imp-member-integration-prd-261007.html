2-3. 마이페이지 계정관리 화면 현황

3. TO-BE — 통합회원 프로세스 설계

요구사항 3~7과 A. 기존회원 소급 일괄통합(1회성 마이그레이션) · B. 신규가입 시 자동통합(상시 로직) · C. 마이페이지 수동연동(번호가 다른 경우, 요구사항 6).

운세당 회원 식별 체계 │ ├─ A. 소급 일괄통합 (기존 회원 전체, 1회성) │ 동일 휴대폰번호로 묶인 계정 그룹 탐색 │ → 그룹 내 "마지막 로그인" 계정 = 대표 계정 (요구사항 4) │ → 나머지 계정의 코인·포인트·이력을 대표 계정으로 이관 │ → 사전 공지 후 시행 (약관 제3조 방식 준용) │ ├─ B. 신규가입 자동통합 (상시) │ 가입 시도 → 휴대폰 인증 단계에서 기존 통합계정 존재 여부 조회 │ → 존재 시: 안내 후 기존 계정으로 연결 (신규 생성 안 함) │ → 미존재 시: 정상 신규가입, 이후 대표 계정이 됨 │ └─ C. 마이페이지 수동연동 (번호가 다른 회원, 요구사항 6) 마이페이지 > 계정 관리 > [계정 연동] 버튼 → 연동할 계정의 아이디/비밀번호 입력으로 소유권 확인 → 연동 완료 시 두 계정의 포인트·코인 합산 (번호가 달라도 합산 — 요구사항 7)

3-1. 플로우 A — 기존회원 소급 일괄통합

  1. 휴대폰번호 기준으로 전체 회원을 그룹핑한다.
  2. 그룹 안에서 마지막 로그인 일시가 가장 최근인 계정을 대표 계정으로 지정한다(요구사항 4 원문 그대로).
  3. 나머지(비대표) 계정의 포인트·상담 코인을 대표 계정으로 합산한다
  4. 상담내역·구매내역·리뷰 등 비금전 이력도 대표 계정에서 통합 조회 가능하도록 연결한다
    이력 레코드를 실제로 이관할지, 원 계정에 둔 채 조회만 통합할지는 §5 C-1 참고.
  5. 시행 전 전체 공지(팝업/이메일/알림 등)로 변경사항을 고지한다 — 개별 사전동의 절차는 두지 않는다

3-2. 플로우 B — 신규가입 시 자동통합(중복 감지)

5개 경로가 휴대폰번호를 확보하는 시점이 서로 다르다는 것이 실사로 확인됐다(§2-1) — 중복 조회 시점도 경로별로 달라진다.

  1. 경로별 번호 확보 시점에 기존 통합계정 존재 여부를 조회한다 — PASS는 인증 완료 시점, 카카오/ 네이버/애플은 OAuth 콜백으로 번호를 넘겨받는 시점, ID/PW는 번호 입력란이 나타나는 가입 단계.
  2. 이미 존재하면 "이미 가입된 번호입니다. 기존 계정으로 진행할까요?" 안내 후, 동의 시 신규 계정을 만들지 않고 기존(대표) 계정 세션으로 로그인시킨다
  3. 존재하지 않으면 정상적으로 신규가입을 진행하고, 해당 계정이 그 번호의 최초(=현재 유일한) 계정이자 대표 계정이 된다.

3-3. 플로우 C — 마이페이지 수동연동

  1. 로그인 상태에서 마이페이지 > 계정 관리에 [계정 연동]
  2. 연동 버튼 클릭 시 연동 대상 계정의 로그인 방식(아이디/비밀번호 등)으로 소유권을 확인한다.
  3. 소유권이 확인되면 두 계정을 연동하고, 번호가 달라도 양쪽의 포인트·코인을 대표 계정으로 합산한다

3-4. 비대표 계정 로그인 처리

통합 후 대표 계정이 아니게 된 가입경로로 재로그인을 시도하면, 별도 안내 없이 자동으로 대표 계정 세션에 연결한다. 사용자는 "어떤 방식으로 로그인해도 내 계정"이라는 경험을 얻는다 — 로그인 시스템 전반의 세션/식별자 처리 변경이 필요하다 (구현 설계는 개발팀 영역).
